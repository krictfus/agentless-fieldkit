# 故障排查

> 第一步永远是：`bash selftest.sh`

## 1. 执行到一半被打断（Ctrl-C / 报错）

`run.sh` 注册了 `trap`，正常/异常/中断都会走收尾：回收公钥 → 删 `tmp/hosts.ini` → 停容器。
如果因为断网、断电、进程被强杀而没有走完，请手动确认四件事：

```bash
ls -l "$HOME"/.ssh/id_rsa_ansible*        # 本地临时私钥是否还在
podman ps -a | grep ansible_workspace   # 容器是否还在跑
podman pod ls                           # 是否残留 compose 建的 pod（名字通常是 tmp）
ls -l tmp/hosts.ini                     # 明文口令文件是否残留
# 目标机上：grep -c ansible_temp ~/.ssh/authorized_keys
```

处理：`bash lib/cleanup_key.sh`（回收公钥并删私钥）；
`podman-compose -f tmp/podman-compose.effective.yml down` 或 `podman pod rm -f tmp` 清理容器。

## 2. 报"公钥回收失败 / FAIL-CLEAN"

这是**保护行为**：只要有一台没清干净，脚本就**不会**删除本地私钥，并把失败清单写到
`tmp/cleanup_failed.txt`，同时打印公钥指纹。常见原因：

- 目标机网络不通、SSH 口令被改；
- 目标机 sshd 端口不是配置里写的那个；
- 目标机 `~/.ssh` 只读或磁盘满。

处理完网络/口令后重跑：`bash lib/cleanup_key.sh`。确认清单清空后私钥会自动删除。
**千万不要**在清单非空时手工删私钥——那样目标机上的公钥就再也没法用同一流程撤销了。

## 3. `summary.txt` 里出现 `MISSING`

清单里有这台主机，但它没出现在 `PLAY RECAP` 里。检查：

- `conf/hosts/*.conf` 里的写法（`IP[:端口] 用户名 密码 [sudo密码]`）；
- `tmp/hosts.ini` 是否真的生成了这台主机；
- 是否被并发/限制参数影响（正常不会）。

## 4. 全部主机 `FAILED`，但明明能 ping 通

先看 `summary.txt` 末尾有没有"诊断提示"：

| run.log 中的标记 | 含义 | 处理 |
|---|---|---|
| `PAYLOAD_NO_ARTIFACT` | 载荷退出码 0 但没写报告 | 对照 `payload/README.md` 检查载荷是否真的写到 `$1` |
| `PAYLOAD_FAILED rc=N` | 载荷自身失败 | 在目标机手动跑一次载荷定位 |
| `unreachable=1` | SSH 不通 | 网络/端口/防火墙 |

**这是本工具刻意做的区分**：不要一看到 FAILED 就去查网络。

## 5. 目标机是老系统（RHEL5/CentOS5 之类）

Ansible 的 `copy`/`file`/`shell` 模块需要目标机有 Python（≥2.6）。
更老或没有 Python 的系统，请改用 `raw` 模块推送执行，或先用 `ssh + cat` 手工取数，
并把这类主机单独记录（不要混在 FAILED 里）。`README.md` 的支持矩阵里有明确下限。

## 6. 容器起不来 / 镜像不存在

```bash
podman image exists krictfus/ansible:2.9 || podman load -i container/ansible-2.9.tar.gz
podman-compose --version      # 没有就先 pip3 install podman-compose
```

`podman-compose` 在多数发行版仓库里没有，用 `pip3` 安装是常态。

## 7. docker 路径起不来（daemon / docker 组 / compose）

v3.6 起支持 podman 与 docker 二选一（`AGENTLESS_RUNTIME=auto|podman|docker`，默认 podman 优先）。
docker 路径有三类常见原因：

1. **daemon 没起**：`docker version` 只有 Client 没有 Server → 启动 `docker` 服务
   （`systemctl enable --now docker`；桌面版是打开 Docker Desktop）。
2. **权限不足**：`permission denied ... /var/run/docker.sock` → 把当前用户加入 `docker` 组并重新登录
   （`sudo usermod -aG docker $USER`）。⚠️ **注意：docker 组等价 root 权限**，只在你自己独占的机器上这么做。
3. **compose 缺失**：`docker compose version` 报未知命令 → 安装 `docker-compose-plugin`；
   只有旧版 `docker-compose` 也能用（适配器会自动回退）。

排障口诀：`AGENTLESS_RUNTIME=podman bash selftest.sh` 与 `AGENTLESS_RUNTIME=docker bash selftest.sh`
各跑一次，哪个绿就用哪个；两个都红，先修环境，不要改代码。

## 8. `podman-compose` 装不上（PEP 668 的三种绕法）

新版发行版（RHEL 9 / Ubuntu 23+）会拦 `pip3 install`：`externally-managed-environment`。
三种绕法，按推荐顺序：

```bash
# ① pipx（隔离环境，最干净）
python3 -m pip install --user pipx && python3 -m pipx install podman-compose

# ② venv（指定位置后加入 PATH）
python3 -m venv ~/.local/podman-compose-venv
~/.local/podman-compose-venv/bin/pip install podman-compose
export PATH="$HOME/.local/podman-compose-venv/bin:$PATH"

# ③ 强行装到系统（最省事，但污染系统 Python）
sudo pip3 install --break-system-packages podman-compose
```

装上后 `command -v podman-compose` 必须能找到；`bootstrap.sh` 与 `selftest.sh` 都以此为准。

## 9. 想换到另一台控制机（迁移）

1. 整个目录复制过去（`container/` 里的大文件也要带上）；
2. `bash bootstrap.sh --install`；
3. `bash selftest.sh`；
4. 用示例载荷 + 一台测试机跑一次 `bash run.sh`。

四步都过，就说明迁移成功——不需要改任何代码。

## 10. 任务产物里的"本机 IP"多出一个 10.88.0.1（实测踩到）

**现象**：用 `collect.example.sh` 自检时，报告里的 IP 是 `192.168.x.x 10.88.0.1`。

**原因**：`podman-compose` 会为 compose 项目创建一个 pod（本项目里叫 `tmp`），
pod 自带 CNI 网络 `10.88.0.0/16`，于是**宿主机上多出一个 10.88.0.1 的接口**；
容器以 `network_mode: host` 与宿主共享网络命名空间，载荷执行时
`hostname -I` / `ip addr` 就会把这个地址一起列出来。

**影响**：如果载荷用"第一个非 lo 的地址"推断本机管理 IP，可能取到 `10.88.0.1`。

**处理**：
- 在载荷的排除列表里加上 `10.88.*`（podman 默认 CNI 网段，与已有的 `172.17.*`、`10.200.*` 同理）；
- 或让载荷改为"取默认路由所在网卡的地址"，这个启发式更稳。

## 11. 结果怎么用

`output/<时间戳>/` 下每台一个 `*_report.html`，`summary.txt` 是分类清单。
框架只产出 `summary.txt` 这一份汇总（漏斗统计 + 五分类 + 被剔除原因），不做"内容级汇总"：产物内容请点开各自文件查看。
## 12. 三层漏斗：为什么有些主机"没被执行到"就结束了

`run.sh` 现在会先用三层漏斗把"注定失败"的主机提前剔掉，避免在它们身上反复等待：

| 层 | 做什么 | 剔除谁 | 归类为 |
|---|---|---|---|
| 第一层 `lib/precheck.sh` | 3 秒超时的 TCP 快探（并行 64，控制端自带 `/dev/tcp`） | SSH 端口连不上 | `UNREACHABLE` |
| 第二层 `lib/push_key.sh` | 并发下发一次性公钥（并行 16） | 端口通、但用户名/口令不对 | `AUTH_FAILED` |
| 第三层 `lib/run_playbook.sh` | 只对下发成功的主机跑 playbook | —— | `OK` / `FAILED` |

所以看到某台主机是 `UNREACHABLE` 或 `AUTH_FAILED` 时，**它根本没有进入执行阶段**，
不是载荷出了问题。`summary.txt` 顶部有漏斗统计，中间有分类结果，底部列出每台被剔除的原因。

想临时关掉漏斗（例如排查"到底是网络问题还是我的预检判断有问题"）：

```bash
bash run.sh --no-precheck
```

**回收范围也改了**：`cleanup_key.sh` 现在只回收"本次真的下发过公钥"的主机（`tmp/push.ok`）。
以前它会对全部清单尝试回收，于是从没碰过的不可达主机会被记成"回收失败"，
进而误触发"保留私钥"的保护——私钥会一直留在控制机上。如果你在旧版本里见过这个现象，原因就是它。
