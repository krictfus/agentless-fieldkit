## 三、逐条说明

### R-01 产物计数写死了载荷的文件名

**现状**

```bash
FILE_COUNT=$(find "$LATEST_OUTPUT" -maxdepth 1 -name '*_report.html' | wc -l)
```

**为什么是错的**

`artifact_suffix` 在 `ansible/vars.yml` 里是变量（默认 `"_report.html"`），而这里把同一个约定
又硬编码了一遍。使用者按文档把后缀改成 `_collect.txt` 后：

- playbook 照常跑、产物照常拉回；
- 只有最后那行"共拉回 N 份产物"变成 **0**。

这违反设计原则 8（**不解析/不假设载荷产物格式**）：框架一旦开始认识产物文件名，就必须
跟着载荷的命名变化去改，而"换任何脚本不改框架"的前提就破了。

**修复**

改为按"目录里除 `run.log` / `summary.txt` 之外的文件数"统计，不出现任何载荷命名假设：

```bash
FILE_COUNT=$(find "$LATEST_OUTPUT" -maxdepth 1 -type f \
    ! -name 'run.log' ! -name 'summary.txt' | wc -l)
```

**验证**：`selftest.sh` 不覆盖（属于展示层计数）；用「改 suffix 后跑一次示例载荷」人工确认（见第五节）。

### R-02 口令里的 `#` 被当成注释截断

**现状**

```bash
_line="${_line%%#*}"          # 从第一个 # 砍到行尾
```

**为什么是错的**

口令里出现 `#` 完全正常（`P@ss#2024`）。上面这行会把它读成 `P@ss`，于是：

- 第二层 `push_key.sh` 认证失败 → 进 `push.fail`；
- 汇总显示 `AUTH_FAILED`，提示"用户名/口令错误或无权限"。

**没有任何报错**，而且提示看起来非常合理——你会先去查账号、查 sshd 配置，很难想到是框架把口令切了。

**修复**

只把「行首」或「空白之后」的 `#` 当注释：

```bash
case "$_line" in ''|'#'*) continue ;; esac   # 整行注释
_line="${_line%%[[:space:]]#*}"              # 行尾注释
```

口令中间/结尾的 `#`（前后都不是空白）原样保留。

**边界（写进契约）**：口令里**不能含空格**——清单以空白分字段，这是原有契约，本次只是把它写明。

### R-03 行尾 `\r` 污染最后一个字段

**现状**：清单用 `while IFS= read -r _line` 读取，未处理 CRLF。

**为什么是错的**

现场大量使用 Windows 记事本编辑 `.conf`。保存后每行以 `\r\n` 结尾，`read` 只按 `\n` 切分，
于是最后一个字段尾部带 `\r`：

```
10.0.0.5 root pass word\r     ← 第四字段（sudo 密码）带 \r
```

结果是 `ansible_become_pass` 里多一个回车 → sudo 拒绝 → 主机分类为 `FAILED`（而不是凭据类错误）。
更隐蔽的是：如果清单**只有三列**（无 sudo 密码），`\r` 会落在第三字段的口令尾部，表现为 `AUTH_FAILED`。

**修复**

```bash
_line="${_line%$'\r'}"
```

**验证**：`selftest.sh` 第 [7] 项用 `printf '...\r\n'` 造了一个 CRLF 行，断言解析结果正确。

### R-04 回收命令没有前置判断

**现状**

```bash
ssh ... "sed -i '/$KEY_TAG/d' ~/.ssh/authorized_keys"
```

**为什么是错的**

目标机如果从来没有 `authorized_keys`（或已被清空），`sed` 报 "No such file" 并返回非 0 →
`clean_remote` 走失败分支 → 写入 `cleanup_failed.txt` → 触发"**保留本地私钥**"的保护。

一次假失败，就让私钥长期留在控制机上；而且下次运行还会重复出现。

**修复**

远端命令先判断文件存在，不存在就直接成功返回：

```bash
f=~/.ssh/authorized_keys; [ -f "$f" ] || exit 0; ...
```

**验证**：逻辑单一，`selftest.sh` 不覆盖（需要远端）；在测试机上手工验证"无 authorized_keys 时返回 0"。

### R-05 固定标签删除会误伤并发实例

**现状**：`KEY_TAG="ansible_temp"` 是固定值，回收时 `sed -i '/ansible_temp/d'` 删除**所有**带该标签的行。

**为什么是错的**

A、B 两组同时在跑（同一批机器、不同网段，或两个操作者）：

1. A 下发公钥（注释 `ansible_temp`）；
2. B 收尾，`sed` 把 A 的公钥一起删了；
3. A 进入执行阶段，认证失败 —— 但 A 的汇总里会显示成 `FAILED`，看起来像"机器有问题"。

**修复**

改为**按公钥本体（base64 那段）精确删除**：

```bash
KEY_BODY="$(awk '{print $2}' "$KEY_PATH.pub")"
grep -vF -- "$KEY_BODY" authorized_keys > tmp && mv tmp authorized_keys
```

只删自己这一把，并发实例互不影响；`KEY_TAG` 仅保留为人类可读注释。

**代价（明牌）**：如果本地私钥被删、只剩标签可依据（手工重跑场景），仍退回按标签删除。

### R-06 `SKIP-EXIST` 只认标签，不认密钥

**现状**

```bash
already=$(ssh ... "grep -c '$KEY_TAG' ~/.ssh/authorized_keys")
if [ "$already" -ge 1 ]; then 记入 push.ok; fi
```

**为什么是错的**

`authorized_keys` 里可能残留**同标签但已过期**的公钥（上次私钥被删、公钥没撤干净）。
这里会判定"已存在"，直接进入执行阶段；认证随即失败，最终分类成 `FAILED`。

**修复**：三处改动

1. 比对**公钥本体**而不是标签；
2. 无论 `SKIP-EXIST` 还是新写入，都用这把私钥**真做一次免密登录**（`BatchMode=yes`）验证；
3. 验证失败记 `FAIL-VERIFY` 并归入 `push.fail`（即 `AUTH_FAILED`），不再拖到执行阶段。

**代价**：每台多一次 SSH 往返（并行下发，实测可忽略）。

---

### R-07 输出目录秒级碰撞（低）

`date +%Y%m%d%H%M%S` 在同一秒内启动两次会得到同一个目录，产物互相覆盖。改为
`date +%Y%m%d%H%M%S_$$`。

## 四、为什么这些问题"以前没发现"

它们的共同点是**不产生错误输出**：

| 现象 | 表面看起来 | 实际 |
|---|---|---|
| R-01 | "这次没拉到产物，可能是机器没产出" | 只是后缀改了，计数逻辑还在找旧名字 |
| R-02 | "这台口令不对，换个人试" | 口令被截断，后几位根本没发出去 |
| R-03 | "这台 sudo 有问题" | 密码末尾多了不可见字符 |
| R-04 | "回收失败，保留私钥更安全" | 目标机压根没有这个文件 |
| R-05 | "B 组跑完，A 组就出问题了" | 公钥被 B 删了 |

所以本轮修复的重点不是"加能力"，而是**让错误尽早、以正确的原因暴露出来**——
这与设计原则 5（快速失败）和 §3.4（五类分类必须指向正确的排查方向）是同一条线。

## 八、给后来者的一句话

这 6 条里，**没有一条能靠"再加一个功能"解决**——它们的修法都是"把假设去掉"：
不再假设产物叫什么、不再假设口令里没有 `#`、不再假设文件一定存在、
不再假设同一时刻只有一个实例在跑。

如果以后要加功能，建议先用同样的问题审一遍：**它引入了哪些新的假设？这些假设不成立时，会不会静默出错？**
